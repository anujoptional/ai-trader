  because each was reachable in production and neither was visible from inside
  a single layer's tests.

  i.  VolumePoller.stamp() fabricated a zero. Under sustained poll failure it
      kept stamping the last reading it had, so the tracker differenced a
      constant and every candle reported volume=0. Reproduced: one good quote
      then 20 failing polls against a healthy price stream gave four closed
      candles reading [0, 0, 0, 0], none of them None. Through the feature
      engine that froze vwap, session_volume and obv, and drove volume_ratio_20
      to 0 -- a maximally strong "dead instrument" signal manufactured out of a
      broker outage, every one flagged ready=True. That violates the rule in
      ARCHITECTURE sections 8 and 9: unavailable beats approximately right, and
      never substitute zero for an unavailable figure. A reading now goes stale
      after a bounded number of missed rounds and stamping stops, so the candle
      reports no volume instead of a false one. The cost is the candle whose
      completing tick went unstamped, which is the right trade.

      Two details are load-bearing and must not be tidied away. A regression in
      the reported total must NOT refresh observed_at, or a permanently stale
      endpoint keeps its stamps looking fresh forever. An UNCHANGED total must
      refresh it, or a genuinely flat instrument would be indistinguishable
      from a dead feed -- which is what keeps a real zero honest. Sizing: the
      live run saw 8 regressions in 147 polls (5.4%), so five consecutive is
      about 5e-7, and the bound fires on real stalls rather than noise.

  ii. CumulativeVolumeTracker attributed a multi-minute span to one minute.
      With readings at minutes 45, 46, then a gap, then 51, the candle at 03:51
      was handed the whole five-minute difference as its volume. Pre-existing,
      reachable with no code changes, and strictly worse once bug i was fixed
      in isolation -- fabricated zeros would have become a fabricated spike,
      and a spike TRIGGERS a scanner where zeros merely suppress it. The
      tracker now requires adjacent minutes and reports no volume across a gap.
      Both fixes had to land together.

1. WHAT THIS IS
---------------

An AI-assisted intraday trading research system for Indian equities (NSE).
Broker today is Groww; Zerodha Kite is a plausible future swap, which is why
all broker specifics sit behind an abstraction.

The purpose is research and validation, not trading. Nothing in this repository
places an order, and nothing should until the whole pipeline has been proven.
The deliberate bias is toward deterministic, hand-checkable arithmetic: every
number a strategy might act on should be reproducible by hand from the candles
that produced it.


2. TARGET ARCHITECTURE
----------------------

    Groww
      |
      +-- Historical candles
      |
      +-- Live ticks
              |
         CandleBuilder        done
              |
          MarketState         done
              |
       FeatureEngine          done  <- newest layer
              |
     Deterministic Scanner    NEXT
              |
         Candidates
              |
      +-------+--------+
      |                |
  Historical       Live / Shadow
   Replay              |
      +-------+--------+
              |
          GPT Brain
              |
     Deterministic Risk
              |
      Position Manager
              |
          Execution

The ordering is the point. The GPT layer sits between two deterministic layers
and can only choose among candidates that deterministic code already approved;
it can never size a position or bypass risk. Do not collapse those boundaries.
Historical replay runs the same deterministic path as live trading, which is
what makes "did the AI add value?" a measurable question. ARCHITECTURE.md
carries the full diagram and each layer's responsibilities.

That diagram is the DATA path. There is also a feedback path: the Position
Manager owns and publishes a PortfolioState snapshot that the Scanner, the GPT
layer and Risk all read. Without it the scanner cannot suppress a name already
at its position limit, the AI cannot emit CLOSE, and Risk cannot enforce max
open positions or daily loss. It adds inputs to the GPT layer, never outputs —
the safety sandwich is unchanged. See ARCHITECTURE.md section 2.2.

5. SETUP ON A NEW DEVICE
------------------------

  git clone https://github.com/anujoptional/ai-trader.git
  cd ai-trader
  scripts/bootstrap.sh

Work happens on main. Python must be 3.12.x (pyproject pins >=3.12,<3.13).

bootstrap.sh needs uv on PATH and does the rest: creates .venv on the
interpreter named in .python-version, fetching that interpreter if the machine
lacks it, then installs the project editable with its dev extras under
constraints.txt, then proves the install by importing ai_trader. Safe to re-run.

Do NOT use pip here. The venv is uv-created and has no pip module at all, so
the older "python -m pip install -e" instruction fails with "No module named
pip". To add a package by hand:

  uv pip install --python .venv/Scripts/python.exe <package>    # Windows
  uv pip install --python .venv/bin/python        <package>     # Linux/macOS

constraints.txt pins the 45 packages the gates were last green against. It is a
constraints file, not a requirements file: pyproject still decides WHAT is
installed and this only bounds WHICH VERSION the resolver may pick, so entries
for packages that go unselected are simply ignored. That is what makes a set
captured on Windows safe to apply unchanged on a Linux CI runner. A real
uv.lock is the intended endpoint and is blocked only by this machine's network
(section 9).

Credentials: copy .env.example to .env and fill it in. .env is gitignored and
must never be committed, printed, or read by an agent (section 7). bootstrap.sh
deliberately does not create it — an .env full of empty values looks configured
and then fails at the broker with a worse message than a missing file does.

  GROWW_TOTP_TOKEN, GROWW_TOTP_SECRET                  broker auth
  OPENAI_API_KEY                                       unused so far
  GITHUB_PAT, GITHUB_USERNAME                          used only by sync.sh

The authoritative list is .env.example, which is a template with empty values
and is safe to read. The loader is load_groww_settings() in
src/ai_trader/config.py; it names only the missing variables, never a value.

Syncing with GitHub uses scripts/sync.sh, which reads the PAT from .env at
invocation and hands it to git through GIT_ASKPASS. The token is never written
into .git/config, never embedded in a remote URL, and never cached by a
credential helper. It refuses to run (exit 2) if .env is missing, the PAT is
empty or still a placeholder, or origin is not an https://github.com/ remote.

  scripts/sync.sh              pull --rebase --autostash, then push
  scripts/sync.sh --dry-run    passed through to git push


6. VERIFY EVERYTHING
--------------------

Interpreter paths below are Windows; substitute .venv/bin/python elsewhere.

Three gates, all of which must pass before any commit:

  .venv/Scripts/python.exe -m ruff format --check .
  .venv/Scripts/python.exe -m ruff check .
  .venv/Scripts/python.exe -m pytest

The same three run in CI on every push and pull request, over a
ubuntu-latest + windows-latest matrix, from .github/workflows/ci.yml. The
matrix earns its keep: this code resolves Asia/Kolkata for NSE session
boundaries, and zoneinfo reads that from the OS on Linux but from the tzdata
package on Windows, so a single-platform run would let the Windows path break
unnoticed. Each gate is a separately named step so a red run names the failing
gate in the job summary. CI supplies no broker credentials and needs none —
every test stubs the broker, so a test that reaches the network fails there.

Two live diagnostics (need real Groww credentials and network):

  .venv/Scripts/python.exe -m ai_trader.cli.check_market_state
  .venv/Scripts/python.exe -m ai_trader.cli.check_features
  .venv/Scripts/python.exe -m ai_trader.cli.check_features --export-csv out.csv

Both back-fill the most recent completed NSE session and print a JSON snapshot.
Exit codes: 0 success, 1 broker/session failure, 2 configuration error. They
work outside market hours, which makes them the fastest end-to-end smoke test.

During market hours, check_features --live continues past the backfill and
folds live ticks through the same engine, which is the only repeatable way to
watch a feature cross the historical-to-live seam:

  .venv/Scripts/python.exe -m ai_trader.cli.check_features --live

The CSV export exists so feature values can be cross-checked against a trusted
external implementation (e.g. TradingView) before a scanner is built on them.


7. HARD CONSTRAINTS
-------------------

From AGENTS.md, non-negotiable:

  - Shadow/paper trading is the default. Never place a live trade unless live
    trading has been explicitly enabled. Do not implement order placement yet.
  - Never hard-code API keys, secrets, passwords, TOTP secrets, or tokens.
    Secrets come from environment variables only. Never print them in logs.
  - Never commit .env.
  - An agent must never read, print, cat, grep, or otherwise expose the
    contents of .env or any credential file. Writing code that loads
    environment variables is fine; inspecting their values is not.
    (.env.example is a template with empty values and is safe to read.)
  - GPT/LLM output must never bypass deterministic risk controls, and position
    sizing must be determined by deterministic code, not by the LLM.
  - Every trading decision should eventually be journaled.
  - Broker-specific logic stays behind the broker abstraction.
  - Do not add Docker, Kubernetes, Redis, MCP, non-SQLite databases, or large
    agent frameworks without a demonstrated requirement.
  - No pandas, NumPy, TA-Lib, or pandas-ta. Indicators are hand-written on
    Decimal so results are exactly reproducible and reviewable.


8. SETTLED DESIGN DECISIONS
---------------------------

Do not relitigate these without a reason; each was chosen deliberately.

  Decimal everywhere, with a pinned Context(prec=28, ROUND_HALF_EVEN).
    Division like 2/22 is non-terminating, so an ambient context would let
    results drift silently. The context traps DivisionByZero, InvalidOperation
    and Overflow, so a bad computation raises instead of producing NaN. Every
    division is explicitly guarded against a zero denominator first. Measured
    cost on this machine is ~8.3 us per feature update — about 4.2 ms per
    minute across 500 instruments, and ~1.7 ms at 200. Irrelevant at one-minute
    resolution, which is what makes the exactness free.

  Timestamps are UTC internally; IST (Asia/Kolkata) is used only for session
    boundaries and the VWAP session key. NSE session is 09:15-15:30 IST.

  CandleBuilder discards the first minute it observes for each instrument.
    A stream is joined mid-minute, so that candle's open is whatever tick was
    seen first rather than the minute's true open, its high/low cover only the
    watched fragment, and it is indistinguishable from a real candle
    downstream. The same minute is also the only one that can never carry
    volume, because cumulative-volume differencing needs a prior reading.
    Discarding it fixes both. Note the minute is still recorded as finalized —
    omitting that lets a late tick reopen it and cost a second real candle.
    This applies to the LIVE path only; historical backfill bypasses the
    builder entirely (MarketState.backfill -> _record_candle_locked).

  Session VWAP is strict: one candle with volume=None disables VWAP for the
    rest of that session rather than reporting a subtly wrong number.

  RSI returns 50 when average gain and average loss are both zero. A flat
    window is normal in illiquid names and must not read as overbought.

  volume_ratio_20 is scoped to the same IST session, and rolling_high_20 /
    rolling_low_20 require a full 20-candle window. A "20-period high" derived
    from 3 candles would be dishonest.

  Readiness invariant, mechanically testable: every flag on FeatureReadiness
    equals (getattr(snapshot, name) is not None). core_ready deliberately
    excludes two whole families. Volume-derived features, because a broker can
    withhold volume for a whole session while trend and volatility stay valid.
    Session-derived features, because an engine started mid-session withholds
    its session aggregates until the next open, so including them would wedge
    core_ready false all day no matter how much price history accumulated.

  warm_up() is literally a loop over update(), so a batch warm-up and an
    incremental live feed produce identical snapshots. There is a test for it.

  Features are pre-warmed from the previous session before the open. core_ready
    needs 50 candles for ema50, so a cold start at 09:15 yields nothing until
    10:05 IST — the most active part of the Indian session. Carrying trend and
    volatility state across the overnight gap costs little: with alpha = 2/51,
    pre-gap data holds roughly 13% of the weight at 10:05 and under 2% by
    11:00. The mechanism already works — warm_up() accepts arbitrary candles,
    VWAP resets on the IST date change, and volume_ratio_20 is same-session
    scoped — so no code change is required, only the wiring. Express the
    overnight gap as an explicit gap_pct feature when the scanner needs it,
    rather than crippling every indicator for the first fifty minutes.

  Every layer owns its own Lock. Broker SDKs deliver ticks on their own feed
    threads, and callbacks fire outside internal locks, so no layer may assume
    the caller serializes it.


9. ENVIRONMENT GOTCHAS
----------------------

These have each cost real time. On Windows specifically:

  - Bare `python` is NOT on PATH; it hits the Windows App Execution Alias and
    prints "Python was not found". Always use .venv/Scripts/python.exe.
  - subprocess.run needs an ABSOLUTE interpreter path, or it raises
    FileNotFoundError [WinError 2].
  - git has core.autocrlf=true and core.safecrlf=true globally, so staging can
    fail with "fatal: LF would be replaced by CRLF". Workaround:
        git -c core.safecrlf=false add -- <paths>
    Any script that rewrites a source file must use newline="" when reading and
    writing, or it will flip the whole file's line endings.
  - Path.read_text(newline=) and Path.write_text(newline=) are Python 3.13+.
    On 3.12 use open(..., newline="") explicitly.
  - In Git Bash, /tmp does not map to the Windows temp directory; use $TEMP.

General:

  - ruff line length is 88 (the default; it is not set in pyproject). E501 is
    the most common gate failure. Run `ruff format .` in write mode before
    checking.
  - The settings loader is load_groww_settings() from ai_trader.config. There
    is no GrowwSettings.from_env().
  - `TZ=Asia/Kolkata date` in Git Bash on Windows returns the WRONG time (it
    reported 06:47 IST when the real time was 12:17 IST). To get IST, use the
    venv python with zoneinfo, never the shell's TZ.

Groww data quirks worth knowing:

  - Groww's live LTP feed carries NO volume. Measured against the live market
    on 2026-09-21: across 114 ticks, not one carried a usable volume, and all
    seven live candles built in that run reported volume=None. The raw payload
    zeroes every field except tsInMillis and ltp. Historical candle volumes are
    per-candle and fine; it is only the live path that is blind.
    The code handles this correctly and that must be preserved. The stream
    parses "volume" as optional (broker/groww_stream.py); Groww sends it as a
    protobuf double where unset is indistinguishable from a real zero, so zero
    is deliberately reported as unknown rather than used as a differencing
    baseline. The live run vindicated that guard — Groww does send volume 0.0,
    and without it every live candle would have anchored on a fabricated
    baseline. The whole chain tolerates absence: MarketTick.cumulative_volume
    is int | None, CandleBuilder skips the volume path on None, and
    CumulativeVolumeTracker reports no volume rather than guessing.
    Consequence WITHOUT a volume source: every volume-derived feature goes
    unavailable from the first live candle and stays that way for the session.
    VolumePoller is that source and removes the consequence, but the guard
    above is what makes its absence safe. Never fabricate volume and never
    substitute zero for an unavailable one.
  - The only live volume Groww serves is the running session total on the REST
    quote endpoint. It was monotonic across eight polls in the same run
    (5,951,700 -> 6,051,078), and re-measured at 13:30-13:32 the same day it
    differenced cleanly at a 15-second cadence (6,709,313 -> 6,716,062, per-poll
    deltas 359 to 2,537 with no resets or gaps). VolumePoller differences it at
    minute boundaries, which is what restored live volume; it is not monotonic
    in practice, though -- the 14:28 run saw 8 regressions in 147 polls, so a
    reading that goes backwards must be rejected rather than differenced.
  - Broker calls fail transiently about half the time. Measured live over 200
    raw quote calls sampled twice a second: 94 failed, every one because Groww
    answered a valid request with a plain-text "404 page not found" body that
    the SDK could not decode (JSONDecodeError). They cluster into short
    outages — 44 of them, the longest 3.6s, most no more than 1s — and the
    failure rate stays high between outages too. GrowwBroker wraps every raw
    call in _retry_broker_call (broker/groww.py): eight attempts, the delay
    doubling from 0.5s until it clears the longest observed outage, then held
    at 2s. Both halves matter. A delay shorter than an outage puts every
    attempt inside it; past that, more attempts beat longer waits, because an
    attempt landing between outages still fails about half the time. The first
    version of this used five attempts and left 3 residual failures in 50 live
    calls; the current one was then re-measured live over the same 50 calls (25
    quote, 25 LTP) and left none. Only the raw call is retried; normalization
    stays outside it so a real schema change surfaces at once instead of being
    hammered eight times. Budget for it: a call can legitimately take seconds.
    The 25 live quote calls took 31.4s in total, so about 1.3s each against a
    nominal sub-second read.
  - AUTHENTICATION is hit by that same 404, and used to be the one broker entry
    point with no retry. Measured live on 2026-09-21, 4 of 8 raw
    GrowwAPI.get_access_token calls failed with "The requested resource was not
    found", so every CLI had a coin-flip chance of dying at startup. It is not
    TOTP reuse: failures landed on freshly generated codes, and a deliberately
    reused code succeeded. authenticate() now goes through the same
    _retry_broker_call, generating the TOTP inside the retried call so an
    attempt that crosses a 30s window uses the code for the window it lands in.
    The access-token type check stays outside the retry, like every other
    normalization step.
  - Because GrowwAuthenticationError subclasses GrowwBrokerError, a CLI that
    catches only the base class blames its own operation for a failure that
    happened before that operation began. All six check_*.py CLIs now catch
    GrowwAuthenticationError first and print "Groww authentication failed."
    tests/test_cli_auth_failures.py asserts this for every one of them, so a
    seventh CLI that forgets the clause fails the suite only if it is added to
    that list — keep _CLI_MODULES there in sync.
  - When backfilling TODAY's in-progress session, the last candle Groww returns
    is PARTIAL and keeps mutating (the 12:22 candle read volume 1799, then 2181
    seconds later). Any live pre-warm must request up to the current minute and
    discard the final candle. The existing CLIs backfill completed prior
    sessions, so none of them hit this.
  - The historical endpoint is end-inclusive, and it DOES serve today's
    in-progress session.
  - Sessions have genuine gaps: minutes with no prints produce no candle. Over
    33 sampled RELIANCE sessions the count ranged 362-376 against 375 regular
    one-minute slots, with gaps concentrated in thin periods and an extra
    closing-auction print at 15:30 IST. Never assume contiguity.
  - The Groww TOTP is single-use per 30-second window. Two authentications in
    quick succession make the second raise GrowwAuthenticationError. Retry with
    ~32s backoff; never re-authenticate in a tight loop.


10. KNOWN DEBT
--------------

None of these are blocking; all are deliberate and recorded.

  1. The feature CSV export renders exact zeros in long decimal form.
  2. volume_ratio_20 is unavailable for the first 20 minutes of every session
     (09:15-09:35 IST) because of same-session scoping — which is prime
     scanning time. The real fix is a time-of-day seasonality-adjusted RVOL.
     Re-verified rather than assumed: _volume_ratio in features/engine.py
     returns None on a short window, never 0, the readiness flag reads False,
     and four tests pin it including the session-rollover case where price
     history carries over but session state does not. This is the
     "unavailable beats approximately right" rule working as designed, so the
     entry is a missing FEATURE, not a bug. Left alone deliberately.
  3. check_features.py has an unreachable `latest is None` guard. Harmless:
     the branch above it already returns when there is no candle. Left in
     place as a cheap invariant rather than deleted.
  4. scripts/sync.sh exports the PAT into the environment of the git pull and
     push subprocesses, so any git hook running under them could read it. This
     repository has no hooks, but close this before taking contributors.
  5. constraints.txt is not a real lock file. It pins versions but records no
     hashes and no resolution graph, so it bounds drift rather than
     eliminating it. A uv.lock is the intended endpoint; generating one needs
     files.pythonhosted.org, which this machine cannot reach (section 9).

  Closed since the last handover, listed so a later session does not re-audit
  them:

  - Candle accepting a zero price: now rejected.
  - No instrument eviction from MarketState: added.
  - _find_recent_completed_session duplicated across three CLIs: extracted to
    cli/_session.py, one copy.
  - CLI duplicate / out-of-order counters structurally pinned at 0: they now
    reflect the real counters.
  - No bootstrap script: scripts/bootstrap.sh.
  - No CI: .github/workflows/ci.yml, Linux + Windows (section 6).
  - No dependency lock: partially — constraints.txt, with the caveat at item 5
    above.
  - No stream supervisor: market/stream.py. It reuses a productive stream,
    rebuilds on a silent session, discards on a retryable failure, backs off
    exponentially with a clamp, and gives up after a bounded number of
    consecutive failures. The error-class split it depends on lives in the
    broker: GrowwStreamConnectionError marks a transport failure worth
    reconnecting for, and its parent GrowwStreamError marks a payload or
    callback failure that must NOT be retried, because replaying it would only
    reproduce the same deterministic fault.


11. NEXT STEPS
--------------

  1. Finish the in-flight work in section 0 -- the feature-layer expansion and
     the live volume source -- before starting anything new. Both are on disk
     and uncommitted. The gates all pass; what remains is the live
     re-validation described in section 0 item h.

     Correcting what an earlier version of this file claimed here, since the
     wrong diagnosis is worth naming: the gap was NOT that MarketState fails to
     forward a volume_enricher to its CandleBuilder. CandleBuilder already
     defaults to CumulativeVolumeTracker and _observe_volume already reads
     tick.cumulative_volume, so that path was live all along. The real cause is
     upstream -- Groww's LTP stream transports volume as a protobuf double
     whose unset value is 0.0, and groww_stream._cumulative_volume deliberately
     maps that zero to None, so no tick ever carries a usable figure. The fix
     is therefore to STAMP the missing value onto the tick before it reaches
     CandleBuilder, not to push snapshots into the tracker: a poller calling
     tracker.observe() directly would roll the tracker's minute over at poll
     time rather than at candle time. Stamping lights up the existing tested
     path with zero changes to CandleBuilder, CumulativeVolumeTracker or
     MarketState. That is what volume_poller.py does, and it was proved live.

  2. DONE 2026-09-22. All 47 features were cross-checked against an
     independently written float64 reference over 362 real RELIANCE candles
     from 2026-09-21, and all 47 agree -- typically to 1e-13 relative or
     better. Three apparent mismatches were each a fault in the reference, not
     in the engine. See docs/FEATURE_VALIDATION.md for the result, the three
     conventions that differ from TradingView, and a hand-checkable row.
     Not a standing guard: the reference used numpy and pandas, which arrive
     under growwapi and which AGENTS.md rules out for our own use, so a
     stdlib-only reference is still owed if this is to run in CI.

  3. Exercise StreamSupervisor against a real session for longer than any
     diagnostic has run so far. PARTLY DONE 2026-09-22: the failure path was
     driven against the real broker during the outage -- three real connect
     attempts, backoff 1s then 2s, failures=3, stopped_because='gave_up',
     nothing escaped, and reconnects=0 because that counter tracks successful
     re-opens while failed opens land in failures. So the give-up bound, the
     backoff schedule, StreamReport accuracy and error containment are live
     facts now, not stub facts.
     What still needs a healthy feed is the success side: tick delivery through
     the supervisor, whether a dropped subscription surfaces as an exception it
     sees or as a stream that simply goes quiet, whether the 60-second
     silent-session window is the right tripwire, reconnect after a session
     that was productive first, and the consecutive-failure counter resetting
     on success. Run it, then tune the constants against what the broker really
     does. Note the TOTP is single-use per 30s, so re-authentication must not
     happen in a tight loop.
     Note also that nothing wires StreamSupervisor into an entry point yet, so
     no shipped code path is supervised.

  4. Then the deterministic scanner (README roadmap item 6). It consumes
     FeatureSnapshot and PortfolioState, not raw candles, and must respect
     readiness flags rather than treating None as zero. Keep it fully
     deterministic — it is the gate that decides what the GPT layer is even
     allowed to see. A scanner result is a research hypothesis, not permission
     to trade.

     Two things to get right from the start, because retrofitting either is
     disruptive. Define PortfolioState — even stubbed empty — and accept it as
     a parameter; a scanner written as a pure function of FeatureSnapshot
     cannot suppress a name already at its position limit. And cap output at N
     candidates per cycle, ranked, with N explicit and tunable (start at 3-5);
     that single number sets LLM cost, rate-limit exposure, and how much
     attention the AI can give each candidate.

  5. Then the historical replay / strategy evaluation engine (README roadmap
     item 7), before the GPT layer rather than after it. It runs the same
     deterministic path over historical candles and measures forward returns,
     MFE/MAE, hit rate, expectancy, drawdown, turnover and cost sensitivity.
     Judge it on net expectancy after realistic costs, not gross hit rate.

     It must take a decision-latency parameter and fill N seconds after the
     signal bar, not at its close. Live, the LLM sits in the middle and the
     order lands seconds later; for momentum setups that bias runs in the
     FAVOURABLE direction, which is how a strategy looks profitable in
     backtest and bleeds in production. Until shadow mode supplies a measured
     N, sweep a range and report sensitivity.

     What this establishes is whether the SCANNER has edge. Whether the AI's
     selection improves on taking every candidate is a different question that
     replay cannot answer — LLM output is non-deterministic and endpoints
     drift, so it is answered only by forward shadow trading. ARCHITECTURE.md
     section 7.1.

Do not skip ahead to the GPT layer. The deterministic candidates are the
control it gets compared against, and they do not exist yet. Note the
corollary: if the AI is ever unavailable at runtime, the default response is no
new entries, rather than trading those candidates unfiltered — they were never
validated as a standalone strategy. That default may be lifted only for a rule
set that has independently passed validation and been explicitly configured as
an approved fallback. "The AI is down" is not itself a reason to trade.
