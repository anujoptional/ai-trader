1. WHAT THIS IS
---------------
An AI-assisted PAPER trader for NSE cash equities: delivery (CNC) longs only,
no live orders anywhere (the broker abstraction has no order methods). Zerodha
Kite Connect is the only broker and data source (Groww was retired and deleted
on Oct 5). Every weekday a scanner scores the top 500 stocks by market cap every
5 minutes; stocks with P(+1% before the close) >= 60% go, with their order book,
futures OI and NSE filings, to three AIs (GPT-6 Luna low = main, GPT-6.1 Sol
low and Claude Sonnet 5.5 low = shadows). Each AI answers BUY or NO_BUY per
stock and keeps its own paper portfolio (+1% target, -1% stop, Rs 2 lakh per
trade). The purpose now is forward evidence: which AI judges these candidates
best. No profitable edge has been established by any research (section 9).

Safety (AGENTS.md is binding): paper only; never read, print or commit .env;
the Kite login stays manual (Zerodha does not allow automated logins); position
sizing and exits are deterministic code, never the LLM; only Kite is active.

2. DAILY OPERATION
------------------
- Nothing to start. Windows scheduled task "AI Trader paper run" (weekdays
  08:30 IST, only while the user is signed in to Windows) runs
  scripts/start_paper_day.cmd =
    .venv\Scripts\python.exe -m ai_trader.cli.run_paper
        --shadow gpt-6.1-sol:low --shadow claude-sonnet-5-5:low --login-wait 360
  A console window ("AI trader paper run") and a Kite login tab open; the run
  waits for the login until 14:30. Log in by about 09:15 for a full day: the
  history load then takes about 9 minutes (650 stocks), the live stream starts
  at 09:14 and scans run 09:40-14:55; the run stops at 15:31.
- It exits at once on weekends, NSE trading holidays (NSE /api/holiday-master,
  e.g. 2026-10-20 Dussehra, 11-08/11-10 Diwali, 11-24, 12-25), after 15:31, or
  when another run is active (lock data/paper/run.lock; a manual start while the
  task runs simply exits).
- Machine: Windows 365 Cloud PC CPC-gupta-BNLA5, IST, sleep never. Keep it
  running and signed in; closing the Remote Desktop window is fine, signing out
  or shutting down stops the run (it starts late when the PC comes back).
- If the 08:30 tab was lost or is stale: close the console window (or
  Stop-ScheduledTask -TaskName 'AI Trader paper run' and stop the python
  processes), then Start-ScheduledTask -TaskName 'AI Trader paper run' or
  double-click scripts\start_paper_day.cmd. A late login still works: the first
  scan fetches every stock (about 4 minutes), later scans use the live stream
  (6-7 seconds).
- Watch: the console, or data/paper/logs/YYYYMMDD.log (same text). One block
  per cycle: "===== HH:MM scan" with NIFTY/VIX, scanner picks and next best,
  the facts each pick gets, each AI's searches/verdicts/cost (tagged
  "[model effort]"), ">>> PAPER BUY" / "<<< PAPER SELL", each AI's portfolio,
  and a day summary at the end.
- After 15:31, compare the AIs (hindsight uses final_bars.json saved at 15:31):
    .\.venv\Scripts\python.exe -m scripts.compare_ai_decisions --day YYYY-MM-DD
  Optional input validation once NSE publishes the day's bhavcopies (evening):
  scripts/validate_paper_inputs.py (see docs/AI_LAYER.md, item 8).
- Change the AIs: edit the --shadow flags in scripts/start_paper_day.cmd
  (MODEL:EFFORT; models are the PRICES keys in ai/openai_client.py; OpenAI
  efforts none..max, Claude efforts low..max). The main AI is OPENAI_MODEL /
  OPENAI_REASONING_EFFORT from .env (default gpt-6-luna, low).
- Remove auto-start: Unregister-ScheduledTask -TaskName 'AI Trader paper run'
  -Confirm:$false. Re-create it (new machine), from the repository root:
    $repo = (Get-Location).Path
    $user = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
    $action = New-ScheduledTaskAction -Execute 'cmd.exe' -Argument "/c `"$repo\scripts\start_paper_day.cmd`"" -WorkingDirectory $repo
    $trigger = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Monday,Tuesday,Wednesday,Thursday,Friday -At '08:30'
    $settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -WakeToRun -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -ExecutionTimeLimit (New-TimeSpan -Hours 10) -MultipleInstances IgnoreNew
    $principal = New-ScheduledTaskPrincipal -UserId $user -LogonType Interactive -RunLevel Limited
    Register-ScheduledTask -TaskName 'AI Trader paper run' -Action $action -Trigger $trigger -Settings $settings -Principal $principal

3. ONE DECISION CYCLE (every 5 minutes, bar close + 5 s, 09:40-14:55)
---------------------------------------------------------------------
a. Universe: data/universe_mcap_20261012/universe.json = the top 500 listed EQ
   stocks by NSE market cap (NSE PR bundle mcap12102026.csv, rank 500 about
   Rs 12,622 crore) + 150 reserves, in rank order; each scan keeps the 500
   highest-ranked stocks that can be scored (scripts/prepare_mcap_universe.py;
   industries from data/universe_nifty500_20261012).
b. Bars: a Kite WebSocket (full mode, 652 instruments incl. NIFTY and INDIAVIX)
   builds minute bars for everything (paper/live.py LiveBars). The whole
   universe is pre-screened on them in about a second; the shortlist (within 5
   points of the threshold, the top 10 and the 5 best F&O stocks) is re-fetched
   from Kite's historical API and re-scored exactly (the validated path). No
   usable stream -> every stock is fetched (about 4 minutes) and that seeds the
   stream's bars (the AI request is stamped after that fetch, so such a cycle's
   bars are 3-5 minutes old: open issue 4). Minutes without a trade = previous
   close, zero volume; a stock with more than 10% such minutes is skipped as
   illiquid.
c. Scanner (scanner/upside.py, model data/models/scanner_up1_by_close_v1,
   CatBoost 223 trees, 31 features): probability that the price touches +1%
   above the buy price (next minute's open) before the session's last
   continuous minute (15:29; 15:14 for F&O stocks since the 2026-08-03 closing
   auction). Fit 2020-01..2025-06 on 213 F&O stocks, early stopping 2025 H2,
   calibration 2026 H1 (raw kept), untouched holdout Jul-Sep 2026: AUC 0.742,
   60-70% band hit 66.2%. Threshold 0.60. Top inputs: time left, ATR, recent
   volatility, i.e. it predicts movement size, not direction. Trained on F&O
   stocks only; its probabilities for non-F&O stocks are untested.
d. Components per candidate: Kite 5-level order book (spread, impact of a Rs 2L
   buy, imbalance, circuit distances), futures (F&O stocks only: premium over
   the stock now from simultaneous quote mids, days to expiry from today, OI
   of the near and next months together now vs the last close, so a rollover is
   not read as positions closed; the previous session's OI change and build-up,
   from both contracts' Kite day bars, withheld when the window starts before
   the last expiry), NSE filings since the previous close / last 7 days /
   material ones (NSE's own subject is the category; routine subjects such as
   trading-window and depository certificates are not material) / board
   meetings next 3 days / corporate actions (data/news/nse_filings.sqlite; at
   start the last 7 days are fetched whole, then today's every cycle), and the
   intraday/daily/market features. Multi-day values (5/20/60-day change, vs
   50/200-day average, vs 250-day high, NIFTY's 20-day change) are measured at
   the current price, not at the last close. Daily history is Kite's, adjusted
   for splits, bonuses, rights and dividends of at least 2% (proven against NSE
   row by row; three demergers are adjusted wrongly: open issue 3).
e. AI request (ai/decision.py DELIVERY_V4, prompt delivery-v4-2026-10-13 from
   the evening of Oct 13; v3 = delivery-v3-2026-10-12 before, user-approved):
   facts only - no scanner probability, stocks alphabetical,
   plain field names (ai/packet.py V3_*), company and industry; batches of 10.
   Web search is required: OpenAI by tool_choice "required"; Claude 5.5 rejects
   a forced tool choice, so its system prompt says to search at least once and
   a reply without a search is asked once more (the first answer is kept if
   that retry fails). Strict JSON per stock, in this order: p_up_first (own
   probability that the price rises 1% before it falls 1%: a price-path
   forecast, not confidence in the verdict), verdict BUY/NO_BUY, reason
   (<= 240 chars). v4 differs from v3 only in that field (v3 called it
   "confidence", after the verdict, and Luna sometimes answered it as
   confidence in NO_BUY). It is stored as verdicts.confidence in the journal.
   Failures, missing answers or a
   spent budget become NO_BUY. Each AI has its own AI_DAILY_BUDGET_USD (default
   $5 per IST day) checked from its journal before every call.
f. Paper buy (paper/broker.py): whole shares worth up to Rs 2 lakh at the
   visible asks of a fresh order book; +1% target (rounded up to the tick) and
   -1% stop set at once, no time limit. One open position and one buy per stock
   per session per AI; max 25 open positions; Rs 50 lakh capital. Charges:
   Zerodha intraday if sold the same session, delivery otherwise.
g. Exits: every minute, 20 s after it, on completed one-minute bars: a bar
   opening beyond a level fills at the open; a bar touching both counts as the
   stop. Positions carry across days in each AI's paper.sqlite.
h. Records (data/paper/, shadows under data/paper/shadows/<model>_<effort>/):
   paper.sqlite (positions + event trail), decisions.sqlite (per call: exact
   request, full reply incl. web searches and source URLs, tokens, cost,
   latency; per stock: verdict, confidence, reason), report/ (trades.csv,
   open_positions.csv, daily.csv, summary.json, report.txt), logs/, capture/
   <date>/<HHMM>.json (raw inputs) + final_bars.json, cache/<date>/ (history).

8. OPEN ISSUES AND NEXT STEPS (ask the user before changing behaviour)
-----------------------------------------------------------------------
Fixed on Oct 13 night, after an audit of what reached the AIs (user-approved;
prompt text unchanged, request fields changed from the Oct 14 run): (1) the
futures premium was the previous closes' (cash close = closing auction,
futures = 30-minute VWAP): PAYTM was sent -1.17% while live it was about
+0.2%, and Sol called it a "futures discount" in 5 of 7 reasons; now live.
(2) days to expiry counted from the previous session; now from today. (3) the
run fetched only today's filings, so filings after the previous close (Oct
12: 386 of 576, incl. 39 results) and weekends were missed; now the last 7
days are fetched at start and retried until done. (4) keyword categories
misread boilerplate ("SEBI" made 1,595 depository certificates "material";
"in order to" made exchange queries "orders"); now NSE's subject is the
category and a fixed list of routine subjects is not material. (5) OI used the
near month only; now near + next, so the rollover before each expiry does not
read as unwinding. (6) multi-day values stopped at the last close (PAYTM at
12:45: 5-day change sent +0.36%, now -4.78%; vs 50-day average +2.54%, now
-2.13%); now at the current price, plus change today. Previous-session
futures fields are named *_prev_session; futures volume/OI was dropped.
scripts/validate_paper_inputs.py checks all of it (put the earlier sessions'
F&O bhavcopies in the --nse folder for the previous-session OI changes).
(7) found by the AI-seat audit, commit 85aee5a: the futures day-bar parser
required close within [low, high], but the close is NSE's settlement price
(30-minute VWAP or theoretical), which can lie outside. SAIL's real bars (Sep 24:
low 185.06, close 184.53) were rejected, so SAIL had no futures facts at all.
Only the open must be in range now.
Fixed on Oct 13 evening (commit after 4c9bb0e): (a) prompt v4 renames
"confidence" to p_up_first and asks for it before the verdict; on the exact
12:35 SHILPAMED request where Luna had said NO_BUY with 0.82, v4 gave Luna
0.26, Sol 0.34, Claude 0.43 (all NO_BUY, real API calls).
compare_ai_decisions now counts verdicts that contradict the AI's own
probability (BUY below 0.4, NO_BUY above 0.6) to watch this. (b) Claude is
asked once more when it answers without a search. (c) the log shows OpenAI
page reads as "read page <url>" instead of searches; the comparison skips
AIs with no calls that day.
1. Structural: the scanner's target (+1% before the close) favours volatile
   stocks that have just fallen; with a -1% stop these lose more often than
   they win (research at 0.60: 48.8% reach +1% before -1%, -0.085% per trade
   after charges). The AIs refuse them, so trades will be rare. Options for the
   user: different exits (e.g. no stop / time exit), a scanner for +1% before
   -1% (research found no direction signal, AUC 0.51), or keep collecting.
2. The scanner is untested on non-F&O stocks (the top-500 universe has ~290).
3. Daily history basis (AI-seat audit; not changed, user's decision). Kite
   adjusts history for corporate actions; everything matches NSE except three
   demergers. Kite's factor vs the market's (NSE ex-date open / cum close): VEDL
   0.523 vs 0.374, TMPV 0.689 vs 0.605, GUJENERGY none vs 0.853. The false drop
   stays in the 250-session window. At the Oct 12 close it shifted VEDL's
   vs_200d_avg to -16.3% (market basis -2.6%) and vs_250d_high to -36.3%
   (-26.4%), with similar errors for GUJENERGY and TMPV. The same values feed the
   scanner (dist_sma200, dist_high250). Separately, Kite adjusts dividends of 2%
   or more, while the scanner's training basis (scripts/build_price_basis.py) does
   not. That moves vs_200d_avg / vs_250d_high by more than 1 point for about 32
   of 600 stocks (CHENNPETRO's 60-day change: 23.4% with its dividend, 18.2%
   without). Options:
   (a) re-scale history before a demerger by NSE's ex-date opening move, as the
       research basis does, using NSE's corporate-action API at start;
   (b) also undo dividend adjustments, so live = training basis;
   (c) exclude the affected stocks;
   (d) accept.
4. Stale full-fetch cycles. Without the stream (the first scan after a late
   login, or a lost stream), the fetch takes 3-5 minutes and the AI request is
   stamped after it. The bars are then 3-5 minutes old while "as_of" says now:
   all Oct 12 requests (no stream then), and the Oct 13 12:00 cycle (no
   candidates that time). Options: skip AI requests whose last bar is more than
   about 60 s old, or re-fetch the shortlist before asking.
5. Not independently checkable: live order-book depth (no historical depth
   exists; internal checks plus the last price against Yahoo's minute range) and
   intraday OI (the previous close is exact; at 14:55 4 of 5 were within 3% of
   NSE's end-of-day OI). Kite can revise the decision minute with late prints:
   1 of 25 on Oct 13, PAYTM 13:10 close 1,595.0 used vs 1,595.7 final.

CURRENT RESEARCH CONTRACT
- Goal: P(TP before SL and within h hours | decision-time features, direction).
  TP and SL have the SAME initial percentage distance from executed entry:
  LONG buy entry, SHORT sell entry, never the future short-cover buy price.
- Both distances use ceil(entry * fraction / tick) * tick, so equality survives
  tick rounding. RELIANCE uses Rs 0.10 ticks. Costs can make net losses exceed
  net gains even when the initial price distances are equal.
- Nine mutually exclusive classes: TP in 0-6/6-15/15-30/30-60 minute bins,
  SL in those same bins, or timeout. Summing TP classes estimates each horizon.
  Joint per-side calibration preserves nondecreasing cumulative probabilities.
- Score = +p_LONG or -p_SHORT for the larger probability; ties abstain.
  Do not amplify scores, apply 2*p-1, or multiply by speed and call it probability.
  Faster opportunities rank higher at a fixed SHORT horizon; increasing the
  horizon for the same setup cannot reduce its cumulative TP probability.

      then 20 failing polls against a healthy price stream gave four closed
      candles reading [0, 0, 0, 0], none of them None. Through the feature
      engine that froze vwap, session_volume and obv, and drove volume_ratio_20
      to 0 -- a maximally strong "dead instrument" signal manufactured out of a
      broker outage, every one flagged ready=True. That violates the rule in
      ARCHITECTURE sections 8 and 9: unavailable beats approximately right, and
      never substitute zero for an unavailable figure. A reading now goes stale
      after a bounded number of missed rounds and stamping stops, so the candle
      reports no volume instead of a false one. The cost is the candle whose
      completing tick went unstamped, which is the right trade.

      the reported total must NOT refresh observed_at, or a permanently stale
      endpoint keeps its stamps looking fresh forever. An UNCHANGED total must
      refresh it, or a genuinely flat instrument would be indistinguishable
      from a dead feed -- which is what keeps a real zero honest. Sizing: the
      live run saw 8 regressions in 147 polls (5.4%), so five consecutive is
      about 5e-7, and the bound fires on real stalls rather than noise.

      With readings at minutes 45, 46, then a gap, then 51, the candle at 03:51
      was handed the whole five-minute difference as its volume. Pre-existing,
      reachable with no code changes, and strictly worse once bug i was fixed
      in isolation -- fabricated zeros would have become a fabricated spike,
      and a spike TRIGGERS a scanner where zeros merely suppress it. The

1. WHAT THIS IS
---------------

An AI-assisted intraday trading research system for Indian equities (NSE).
Broker today is Groww; Zerodha Kite is a plausible future swap, which is why
all broker specifics sit behind an abstraction. The swap has already been
priced: costs/ models BOTH published fee schedules, and at the one-lakh clip
this system trades they cost the same to the paisa (section 11 item 5).

The purpose is research and validation, not trading. Nothing in this repository
places an order, and nothing should until the whole pipeline has been proven.
The deliberate bias is toward deterministic, hand-checkable arithmetic: every
number a strategy might act on should be reproducible by hand from the candles
that produced it.


2. TARGET ARCHITECTURE
----------------------

    Groww
      |
      +-- Historical candles
      |
      +-- Live ticks
              |
         CandleBuilder        done
              |
          MarketState         done
              |
       FeatureEngine          done
              |
     Deterministic Scanner    done
              |
         Candidates
              |
      +-------+--------+
      |                |
  Historical       Live / Shadow
   Replay   done       |
      +-------+--------+
              |
          GPT Brain
              |
     Deterministic Risk
              |
      Position Manager
              |
          Execution

Historical Replay is the newest layer -- built, run, and reporting; see section
11 item 7. Everything from GPT Brain down is still unbuilt.

The ordering is the point. The GPT layer sits between two deterministic layers
and can only choose among candidates that deterministic code already approved;
it can never size a position or bypass risk. Do not collapse those boundaries.
Historical replay runs the same deterministic path as live trading, which is
what makes "did the AI add value?" a measurable question. ARCHITECTURE.md
carries the full diagram and each layer's responsibilities.

That diagram is the DATA path. There is also a feedback path: the Position
Manager owns and publishes a PortfolioState snapshot that the Scanner, the GPT
layer and Risk all read. Without it the scanner cannot suppress a name already
at its position limit, the AI cannot emit CLOSE, and Risk cannot enforce max
open positions or daily loss. It adds inputs to the GPT layer, never outputs —
the safety sandwich is unchanged. See ARCHITECTURE.md section 2.2.

    (scanner/feasibility.py). TWO schedules are modelled, Groww and
    Zerodha/Kite, because rule 10 in AGENTS.md makes the second a plausible

    against a schedule worked by hand, for both -- but the rates are published
    tables transcribed, NEITHER checked against a real contract note,
    and the spread is absent entirely because no layer produces one. The screen
    prices the hurdle PER NAME: it sizes the clip at the snapshot's close
    through the same SizingPolicy the decision will use, because the clip is a
    FLOOR on turnover -- whole shares round it UP, never down -- so a dear name
    fills well above a lakh and pays a smaller fraction than the full-clip
    figure says. Screening it against that figure would be too STRICT, not too

    reaching past the config -- stating it once in the object both replay and
    live build from is the stronger form of the same rule, not an abandonment
    of it. Three is calibration against the cost arithmetic rather than
    evidence about what trades well: a one-lakh hurdle is about 0.083% of
    notional and a liquid large cap's one-minute ATR sits near 0.05%-0.15% of
    price, so three puts the cut inside that band instead of above or below all
    of it. Section 7's placeholder warning applies to it like everything else.
    See ARCHITECTURE.md sections 1.4 and 4.4.

Built and measured -- the newest layer, section 11 item 7:

  - Shared strategy configuration (strategy/config.py, 287 lines;
    strategy/exits.py, 283). ONE StrategyConfig object states size, costs,
    rules, screen, exits and book limits, and everything downstream derives
    from it rather than restating any of it. This is what makes "identical
    treatment, identical parameters" enforceable instead of aspirational: a
    sweep cannot quietly diverge from what live would run, because there is no
    second place to write a parameter down. ScannerConfig is built FROM it, so
    the fork between replay and live sits strictly ABOVE the scanner -- both
    sides feed the scanner the same object and read the same candidates out.
  - Candle cache / history store (history/store.py, 476 lines). Per-symbol,
    per-day CSV under a cache root. Coverage is derived from the bars
    themselves rather than from a manifest, so a cache that is missing a minute
    reports the gap instead of hiding it; --offline then fails loudly rather
    than filling it from the vendor. Unknown volume is written as an EMPTY
    field, never as 0 -- see the None-versus-zero rule in section 13.
  - Replay engine (replay/, 2,059 lines across engine / models / portfolio /
    report) and its CLI (cli/backtest.py, 446). A cached candle enters
    MarketState exactly where a candle assembled from live ticks enters it, so
    from that boundary onward replay and live share one path: same features,
    same Scanner, same StrategyConfig, same candidates. The only difference
    upstream is how the candle was obtained -- fetched whole, versus built from
    ticks. Downstream, replay books those candidates through a portfolio with
    a stated fill model (latency, half spread, slippage, and an explicit choice
    of how to resolve a bar that touched both stop and target). The fill model
    has NO default: a caller passes --frictionless or passes all three figures,
    because a silent zero is the most flattering assumption a backtest can
    make. Validated end to end; its measurements are in backtests/README.md.

Not built: GPT integration, risk, position management, execution, journaling.
PortfolioState exists as a contract with an empty() constructor, but nothing
outside replay populates it -- the position manager that would is not built,
which is why a live scan still sees an empty book and therefore an upper bound
on the candidate rate.

5. SETUP ON A NEW DEVICE
------------------------

  git clone https://github.com/anujoptional/ai-trader.git
  cd ai-trader
  scripts/bootstrap.sh

Work happens on main. Python must be 3.12.x (pyproject pins >=3.12,<3.13).

bootstrap.sh needs uv on PATH and does the rest: creates .venv on the
interpreter named in .python-version, fetching that interpreter if the machine
lacks it, then installs the project editable with its dev extras under
constraints.txt, then proves the install by importing ai_trader. Safe to re-run.

Do NOT use pip here. The venv is uv-created and has no pip module at all, so
the older "python -m pip install -e" instruction fails with "No module named
pip". To add a package by hand:

  uv pip install --python .venv/Scripts/python.exe <package>    # Windows
  uv pip install --python .venv/bin/python        <package>     # Linux/macOS

constraints.txt pins the 45 packages the gates were last green against. It is a
constraints file, not a requirements file: pyproject still decides WHAT is
installed and this only bounds WHICH VERSION the resolver may pick, so entries
for packages that go unselected are simply ignored. That is what makes a set
captured on Windows safe to apply unchanged on a Linux CI runner. A real
uv.lock is the intended endpoint and is blocked only by this machine's network
(section 9).

Credentials: copy .env.example to .env and fill it in. .env is gitignored and
must never be committed, printed, or read by an agent (section 7). bootstrap.sh
deliberately does not create it — an .env full of empty values looks configured
and then fails at the broker with a worse message than a missing file does.

  GROWW_TOTP_TOKEN, GROWW_TOTP_SECRET                  broker auth
  OPENAI_API_KEY                                       unused so far
  GITHUB_PAT, GITHUB_USERNAME                          used only by sync.sh

The authoritative list is .env.example, which is a template with empty values
and is safe to read. The loader is load_groww_settings() in
src/ai_trader/config.py; it names only the missing variables, never a value.

Syncing with GitHub uses scripts/sync.sh, which reads the PAT from .env at
invocation and hands it to git through GIT_ASKPASS. The token is never written
into .git/config, never embedded in a remote URL, and never cached by a
credential helper. It refuses to run (exit 2) if .env is missing, the PAT is
empty or still a placeholder, or origin is not an https://github.com/ remote.

  scripts/sync.sh              pull --rebase --autostash, then push
  scripts/sync.sh --dry-run    passed through to git push


6. VERIFY EVERYTHING
--------------------

Interpreter paths below are Windows; substitute .venv/bin/python elsewhere.

Three gates, all of which must pass before any commit:

  .venv/Scripts/python.exe -m ruff format --check .
  .venv/Scripts/python.exe -m ruff check .
  .venv/Scripts/python.exe -m pytest

The same three run in CI on every push and pull request, over a
ubuntu-latest + windows-latest matrix, from .github/workflows/ci.yml. The
matrix earns its keep: this code resolves Asia/Kolkata for NSE session
boundaries, and zoneinfo reads that from the OS on Linux but from the tzdata
package on Windows, so a single-platform run would let the Windows path break
unnoticed. Each gate is a separately named step so a red run names the failing
gate in the job summary. CI supplies no broker credentials and needs none —
every test stubs the broker, so a test that reaches the network fails there.

Three end-to-end diagnostics (need real Groww credentials and network):

  .venv/Scripts/python.exe -m ai_trader.cli.check_market_state
  .venv/Scripts/python.exe -m ai_trader.cli.check_features
  .venv/Scripts/python.exe -m ai_trader.cli.check_features --export-csv out.csv
  .venv/Scripts/python.exe -m ai_trader.cli.check_scanner

All three back-fill the most recent completed RELIANCE session and print a JSON
snapshot; check_scanner carries the same snapshot the rest of the way and
prints what the rules made of it. Exit codes: 0 success, 1 broker/session
failure, 2 configuration error. They work outside market hours, which makes
them the fastest end-to-end smoke test.

During market hours, check_features --live and check_scanner --live continue
past the backfill and fold live ticks through the same engine, which is the
only repeatable way to watch a feature cross the historical-to-live seam:

  .venv/Scripts/python.exe -m ai_trader.cli.check_features --live
  .venv/Scripts/python.exe -m ai_trader.cli.check_scanner --live

The CSV export exists so feature values can be cross-checked against a trusted
external implementation (e.g. TradingView) before a scanner is built on them.

One diagnostic needs neither credentials nor a session, and is the one to reach
for when the market is shut:

  .venv/Scripts/python.exe -m ai_trader.cli.check_costs
  .venv/Scripts/python.exe -m ai_trader.cli.check_costs 2450 100
  .venv/Scripts/python.exe -m ai_trader.cli.check_costs --broker zerodha

It prints round-trip cost by clip size, the same sizes under BOTH schedules
side by side, both readings of the stated target, and the sized estimate with
both exits at each quote. --broker takes groww, zerodha or kite and defaults
to groww, which is the broker this system connects to and not the cheaper of
the two. No broker call, no configuration, therefore no exit code 2 -- only 0,
or 1 on an unusable price argument or an unknown broker name.

One command in cli/ is not a diagnostic at all. cli.backtest replays the
scanner over cached history and reports what its candidates earned:

  .venv/Scripts/python.exe -m ai_trader.cli.backtest \
    --symbols-file backtests/universe.txt \
    --start 2026-07-01 --end 2026-09-24 --offline \
    --latency-seconds 1 --half-spread 0.0002 --slippage 0.0001 \
    --stop-atr 2.0 --label fixed-2.0

With --offline it loads no credentials and makes no vendor call, so a published
run reproduces exactly; it reads the cached tape only and fails loudly on a gap
rather than filling it from whatever the broker serves today. Filling that
cache in the first place needs a broker and no --offline. The fill model has NO
default: pass --frictionless or pass all three friction figures. Every
strategy flag parses to None and is forwarded only when actually passed, so
StrategyConfig stays the only place a parameter is written down. Exit codes
match the checks: 0, 1, 2. The twelve published rows and the flags that
reproduce them are in backtests/README.md.


7. HARD CONSTRAINTS
-------------------

From AGENTS.md, non-negotiable:

  - Shadow/paper trading is the default. Never place a live trade unless live
    trading has been explicitly enabled. Do not implement order placement yet.
  - Never hard-code API keys, secrets, passwords, TOTP secrets, or tokens.
    Secrets come from environment variables only. Never print them in logs.
  - Never commit .env.
  - An agent must never read, print, cat, grep, or otherwise expose the
    contents of .env or any credential file. Writing code that loads
    environment variables is fine; inspecting their values is not.
    (.env.example is a template with empty values and is safe to read.)
  - GPT/LLM output must never bypass deterministic risk controls, and position
    sizing must be determined by deterministic code, not by the LLM.
  - Every trading decision should eventually be journaled.
  - Broker-specific logic stays behind the broker abstraction.
  - Do not add Docker, Kubernetes, Redis, MCP, non-SQLite databases, or large
    agent frameworks without a demonstrated requirement.
  - No pandas, NumPy, TA-Lib, or pandas-ta. Indicators are hand-written on
    Decimal so results are exactly reproducible and reviewable.


8. SETTLED DESIGN DECISIONS
---------------------------

Do not relitigate these without a reason; each was chosen deliberately.

  Decimal everywhere, with a pinned Context(prec=28, ROUND_HALF_EVEN).
    Division like 2/22 is non-terminating, so an ambient context would let
    results drift silently. The context traps DivisionByZero, InvalidOperation
    and Overflow, so a bad computation raises instead of producing NaN. Every
    division is explicitly guarded against a zero denominator first. Measured
    cost on this machine is ~8.3 us per feature update — about 4.2 ms per
    minute across 500 instruments, and ~1.7 ms at 200. Irrelevant at one-minute
    resolution, which is what makes the exactness free.

  Everything is IST. There is one clock -- src/ai_trader/clock.py, a top-level
    leaf that imports nothing from ai_trader so that broker can reach it too --
    and every layer reads it. Timestamps are NORMALIZED to IST at each
    boundary, not merely made timezone-aware. That distinction is invisible to
    arithmetic, because an aware UTC instant and an aware IST instant compare
    and hash identically; it is not invisible to .date(), .hour or a cached CSV
    filename, each of which answers a LOCAL question, and UTC and IST disagree
    about the date between 00:00 and 05:30 local. NSE session is 09:15-15:30
    IST. This file used to say timestamps were UTC internally with IST reserved
    for session boundaries and the VWAP key. That was wrong about the code and
    is corrected here; if you find the old wording anywhere else, it is stale.

  CandleBuilder discards the first minute it observes for each instrument.
    A stream is joined mid-minute, so that candle's open is whatever tick was
    seen first rather than the minute's true open, its high/low cover only the
    watched fragment, and it is indistinguishable from a real candle
    downstream. The same minute is also the only one that can never carry
    volume, because cumulative-volume differencing needs a prior reading.
    Discarding it fixes both. Note the minute is still recorded as finalized —
    omitting that lets a late tick reopen it and cost a second real candle.
    This applies to the LIVE path only; historical backfill bypasses the
    builder entirely (MarketState.backfill -> _record_candle_locked).

  Session VWAP is strict: one candle with volume=None disables VWAP for the
    rest of that session rather than reporting a subtly wrong number.

  RSI returns 50 when average gain and average loss are both zero. A flat
    window is normal in illiquid names and must not read as overbought.

  volume_ratio_20 is scoped to the same IST session, and rolling_high_20 /
    rolling_low_20 require a full 20-candle window. A "20-period high" derived
    from 3 candles would be dishonest.

  Readiness invariant, mechanically testable: every flag on FeatureReadiness
    equals (getattr(snapshot, name) is not None). core_ready deliberately
    excludes two whole families. Volume-derived features, because a broker can
    withhold volume for a whole session while trend and volatility stay valid.
    Session-derived features, because an engine started mid-session withholds
    its session aggregates until the next open, so including them would wedge
    core_ready false all day no matter how much price history accumulated.

  warm_up() is literally a loop over update(), so a batch warm-up and an
    incremental live feed produce identical snapshots. There is a test for it.

  Features are pre-warmed from the previous session before the open. core_ready
    needs 50 candles for ema50, so a cold start at 09:15 yields nothing until
    10:05 IST — the most active part of the Indian session. Carrying trend and
    volatility state across the overnight gap costs little: with alpha = 2/51,
    pre-gap data holds roughly 13% of the weight at 10:05 and under 2% by
    11:00. The mechanism already works — warm_up() accepts arbitrary candles,
    VWAP resets on the IST date change, and volume_ratio_20 is same-session
    scoped — so no code change is required, only the wiring. Express the
    overnight gap as an explicit gap_pct feature when the scanner needs it,
    rather than crippling every indicator for the first fifty minutes.

  Every layer owns its own Lock. Broker SDKs deliver ticks on their own feed
    threads, and callbacks fire outside internal locks, so no layer may assume
    the caller serializes it.


9. ENVIRONMENT GOTCHAS
----------------------

These have each cost real time. On Windows specifically:

  - Bare `python` is NOT on PATH; it hits the Windows App Execution Alias and
    prints "Python was not found". Always use .venv/Scripts/python.exe.
  - subprocess.run needs an ABSOLUTE interpreter path, or it raises
    FileNotFoundError [WinError 2].
  - git has core.autocrlf=true and core.safecrlf=true globally, so staging can
    fail with "fatal: LF would be replaced by CRLF". Workaround:
        git -c core.safecrlf=false add -- <paths>
    Any script that rewrites a source file must use newline="" when reading and
    writing, or it will flip the whole file's line endings.
  - Path.read_text(newline=) and Path.write_text(newline=) are Python 3.13+.
    On 3.12 use open(..., newline="") explicitly.
  - In Git Bash, /tmp does not map to the Windows temp directory; use $TEMP.

General:

  - ruff line length is 88 (the default; it is not set in pyproject). E501 is
    the most common gate failure. Run `ruff format .` in write mode before
    checking.
  - The settings loader is load_groww_settings() from ai_trader.config. There
    is no GrowwSettings.from_env().
  - `TZ=Asia/Kolkata date` in Git Bash on Windows returns the WRONG time (it
    reported 06:47 IST when the real time was 12:17 IST). To get IST, use the
    venv python with zoneinfo, never the shell's TZ.

Groww data quirks worth knowing:

  - Groww's live LTP feed carries NO volume. Measured against the live market
    on 2026-09-21: across 114 ticks, not one carried a usable volume, and all
    seven live candles built in that run reported volume=None. The raw payload
    zeroes every field except tsInMillis and ltp. Historical candle volumes are
    per-candle and fine; it is only the live path that is blind.
    The code handles this correctly and that must be preserved. The stream
    parses "volume" as optional (broker/groww_stream.py); Groww sends it as a
    protobuf double where unset is indistinguishable from a real zero, so zero
    is deliberately reported as unknown rather than used as a differencing
    baseline. The live run vindicated that guard — Groww does send volume 0.0,
    and without it every live candle would have anchored on a fabricated
    baseline. The whole chain tolerates absence: MarketTick.cumulative_volume
    is int | None, CandleBuilder skips the volume path on None, and
    CumulativeVolumeTracker reports no volume rather than guessing.
    Consequence WITHOUT a volume source: every volume-derived feature goes
    unavailable from the first live candle and stays that way for the session.
    VolumePoller is that source and removes the consequence, but the guard
    above is what makes its absence safe. Never fabricate volume and never
    substitute zero for an unavailable one.
  - The only live volume Groww serves is the running session total on the REST
    quote endpoint. It was monotonic across eight polls in the same run
    (5,951,700 -> 6,051,078), and re-measured at 13:30-13:32 the same day it
    differenced cleanly at a 15-second cadence (6,709,313 -> 6,716,062, per-poll
    deltas 359 to 2,537 with no resets or gaps). VolumePoller differences it at
    minute boundaries, which is what restored live volume; it is not monotonic
    in practice, though -- the 14:28 run saw 8 regressions in 147 polls, so a
    reading that goes backwards must be rejected rather than differenced.
  - Broker calls fail transiently about half the time. Measured live over 200
    raw quote calls sampled twice a second: 94 failed, every one because Groww
    answered a valid request with a plain-text "404 page not found" body that
    the SDK could not decode (JSONDecodeError). They cluster into short
    outages — 44 of them, the longest 3.6s, most no more than 1s — and the
    failure rate stays high between outages too. GrowwBroker wraps every raw
    call in _retry_broker_call (broker/groww.py): eight attempts, the delay
    doubling from 0.5s until it clears the longest observed outage, then held
    at 2s. Both halves matter. A delay shorter than an outage puts every
    attempt inside it; past that, more attempts beat longer waits, because an
    attempt landing between outages still fails about half the time. The first
    version of this used five attempts and left 3 residual failures in 50 live
    calls; the current one was then re-measured live over the same 50 calls (25
    quote, 25 LTP) and left none. Only the raw call is retried; normalization
    stays outside it so a real schema change surfaces at once instead of being
    hammered eight times. Budget for it: a call can legitimately take seconds.
    The 25 live quote calls took 31.4s in total, so about 1.3s each against a
    nominal sub-second read.
  - AUTHENTICATION is hit by that same 404, and used to be the one broker entry
    point with no retry. Measured live on 2026-09-21, 4 of 8 raw
    GrowwAPI.get_access_token calls failed with "The requested resource was not
    found", so every CLI had a coin-flip chance of dying at startup. It is not
    TOTP reuse: failures landed on freshly generated codes, and a deliberately
    reused code succeeded. authenticate() now goes through the same
    _retry_broker_call, generating the TOTP inside the retried call so an
    attempt that crosses a 30s window uses the code for the window it lands in.
    The access-token type check stays outside the retry, like every other
    normalization step.
  - Because GrowwAuthenticationError subclasses GrowwBrokerError, a CLI that
    catches only the base class blames its own operation for a failure that
    happened before that operation began. All seven broker-facing check_*.py
    CLIs catch GrowwAuthenticationError first and print "Groww authentication
    failed." tests/test_cli_auth_failures.py asserts this for every one of
    them, so an eighth CLI that forgets the clause fails the suite only if it
    is added to that list — keep _CLI_MODULES there in sync. That warning was
    not hypothetical: check_scanner shipped WITH the clause and was left out
    of _CLI_MODULES, so for several sessions nothing pinned it. Added
    2026-09-29. cli/backtest.py is the deliberate exception -- it catches the
    base class, because its only authentication call site is already reporting
    authentication and so has nothing else to blame.
  - When backfilling TODAY's in-progress session, the last candle Groww returns
    is PARTIAL and keeps mutating (the 12:22 candle read volume 1799, then 2181
    seconds later). Any live pre-warm must request up to the current minute and
    discard the final candle. The existing CLIs backfill completed prior
    sessions, so none of them hit this.
  - The historical endpoint is end-inclusive, and it DOES serve today's
    in-progress session.
  - Sessions have genuine gaps: minutes with no prints produce no candle. Over
    33 sampled RELIANCE sessions the count ranged 362-376 against 375 regular
    one-minute slots, with gaps concentrated in thin periods and an extra
    closing-auction print at 15:30 IST. Never assume contiguity.
  - The Groww TOTP is single-use per 30-second window. Two authentications in
    quick succession make the second raise GrowwAuthenticationError. Retry with
    ~32s backoff; never re-authenticate in a tight loop.


10. KNOWN DEBT
--------------

None of these are blocking; all are deliberate and recorded.

  1. The feature CSV export renders exact zeros in long decimal form.
  2. volume_ratio_20 is unavailable for the first 20 minutes of every session
     (09:15-09:35 IST) because of same-session scoping — which is prime
     scanning time. The real fix is a time-of-day seasonality-adjusted RVOL.
     Re-verified rather than assumed: _volume_ratio in features/engine.py
     returns None on a short window, never 0, the readiness flag reads False,
     and four tests pin it including the session-rollover case where price
     history carries over but session state does not. This is the
     "unavailable beats approximately right" rule working as designed, so the
     entry is a missing FEATURE, not a bug. Left alone deliberately.
  3. check_features.py has an unreachable `latest is None` guard. Harmless:
     the branch above it already returns when there is no candle. Left in
     place as a cheap invariant rather than deleted.
  4. scripts/sync.sh exports the PAT into the environment of the git pull and
     push subprocesses, so any git hook running under them could read it. This
     repository has no hooks, but close this before taking contributors.
  5. constraints.txt is not a real lock file. It pins versions but records no
     hashes and no resolution graph, so it bounds drift rather than
     eliminating it. A uv.lock is the intended endpoint; generating one needs
     files.pythonhosted.org, which this machine cannot reach (section 9).

  Closed since the last handover, listed so a later session does not re-audit
  them:

  - Candle accepting a zero price: now rejected.
  - No instrument eviction from MarketState: added.
  - _find_recent_completed_session duplicated across three CLIs: extracted to
    cli/_session.py, one copy.
  - CLI duplicate / out-of-order counters structurally pinned at 0: they now
    reflect the real counters.
  - No bootstrap script: scripts/bootstrap.sh.
  - No CI: .github/workflows/ci.yml, Linux + Windows (section 6).
  - No dependency lock: partially — constraints.txt, with the caveat at item 5
    above.
  - No stream supervisor: market/stream.py. It reuses a productive stream,
    rebuilds on a silent session, discards on a retryable failure, backs off
    exponentially with a clamp, and gives up after a bounded number of
    consecutive failures. check_features --live drives its window through it;
    the other two stream CLIs are bounded probes and stay unsupervised. The
    error-class split it depends on lives in the broker:
    GrowwStreamConnectionError marks a transport failure worth reconnecting
    for, and its parent GrowwStreamError marks a payload or callback failure
    that must NOT be retried, because replaying it would only reproduce the
    same deterministic fault.

  4. DONE 2026-09-22: the deterministic scanner (README roadmap item 6), in
     scanner/ with tests in tests/test_scanner.py. Both retrofit hazards were
     taken at the start: PortfolioState is a parameter from the first commit
     (stubbed via PortfolioState.empty(), since the position manager does not
     exist), and output is capped at ScannerConfig.max_candidates, default 5,
     with ScanResult.truncated reporting what the cap discarded.

     Four things learned while building it, each worth more than the code:

     a) The rolling window INCLUDES the candle being measured, so
        close > rolling_high_20 is unsatisfiable and a breakout rule written
        the obvious way emits nothing all session without ever erroring.
        BreakoutRule tests ATR-scaled closeness to the window edge instead,
        and the test that pins this drives the real FeatureEngine rather than
        a fixture -- a fixture can assert the convenient thing while the
        engine does the other.

     b) Volume splits two ways and the distinction is load-bearing. A rule
        that NEEDS volume (vwap_reversion) is skipped when it is missing. A
        rule that merely PREFERS it (range_breakout) scores without it rather
        than averaging against zero; substituting zero would mark down every
        breakout in the first twenty minutes of a session, which is exactly
        when volume_ratio_20 does not yet exist.

     c) Read every feature through its own readiness flag, never through
        `is not None` -- that is the section 4.3 trap made structural. The
        subtlety is in TESTING it: withholding a feature does NOT prove the
        defence, because it removes the value along with the flag and a rule
        that skipped the flag entirely would decline anyway. The test has to
        build a snapshot whose flags and values DISAGREE. A mutation probe
        caught this: deleting the flag check from available() left all 39
        tests green. After adding _divergent_snapshot the same mutation fails
        6 tests.

     d) Mutation probing is worth doing on any property a docstring claims to
        defend. Six probes were run against the finished layer -- strict
        breakout, zero-for-unknown volume, fail-open session window, ranking
        without tiebreakers, summed instead of maxed scores, silently merged
        duplicate snapshots -- and all six were caught. That is a cheap way
        to tell a test that passes from a test that defends.

     Deliberately NOT decided here, and left for replay: whether a 0.8 from
     one rule means what a 0.8 from another does (the scanner ranks across
     rules as if it did, because it must rank somehow), and whether two rules
     agreeing deserves a bonus (it gets none -- both names are recorded and
     the higher score wins). Every threshold in rules.py is a conventional
     level, not a measurement; section 7 of ARCHITECTURE.md applies to all of

  5. DONE 2026-09-23: the transaction cost model (costs/) and the feasibility
     screen that consumes it (scanner/feasibility.py). Not a roadmap item --
     built as a precondition for the scanner answering the only question that
     matters before any rule fires: can a move worth capturing even be had at
     this position size?

     The user's objective, in their words, is "many trades of small profits
     through the day across good quality promisingly poised liquid stock",
     exiting "as soon as they reach a small upside above costs of trading,
     lets say around 0.2% in total or maybe even 0.1%". Shorts are in scope.

     The thing to understand before touching any of this: THAT TARGET CANNOT BE
     A CONSTANT, and the cost table is why. At Groww's rates a round trip costs
     0.2715% of a Rs 20,000 clip and 0.0827% of a Rs 1,00,000 one, because
     brokerage caps at Rs 20 per leg and the cap stops binding above Rs 20,000
     a leg. So 0.2% gross is a LOSS at the first size and a PROFIT at the
     second. Any single percentage written into the code is silently wrong at
     every size but one -- and wrong at a DIFFERENT size under each schedule,
     since Zerodha charges 0.03% and so does not reach the same cap until
     Rs 66,666.67. What the system holds is the shape --

       required gross = round-trip cost at this size + the margin asked for

     -- with both terms supplied by the caller, and the schedule supplied too.
     Section 7.2 of ARCHITECTURE.md is the principle; this is it made
     arithmetic.

     Four things learned building it:

     a) UNITS ARE THE WHOLE BALLGAME. FeatureSnapshot.atr_pct is
        safe_divide(atr14, close) with NO multiplication by 100 -- it is a
        FRACTION despite the name. Every rate in costs/ is therefore also a
        fraction and is named with a _fraction suffix for that reason alone.
        Mixing a fraction with a percentage is a 100x error that type-checks,
        runs, and prints a plausible number. The tests reconcile charges in
        RUPEES rather than against each other, because rupees is where such an
        error is visible.

     b) The brokerage cap is PER LEG. Applying it to the round trip would halve
        the brokerage on exactly the positions where it binds, and the total
        would still look like a plausible cost. Both schedules cap at the same
        Rs 20 and differ ONLY in the rate that reaches it, so above
        Rs 66,666.67 a leg they are the same number -- the cap is where the two
        converge, not where they part.

     c) The screen multiplies, never divides: required > max_atr_multiple *
        atr_fraction, not required / atr_fraction > multiple. A zero ATR is a
        real reading on a stock that has not moved, and dividing by it would
        raise on precisely the names the screen exists to reject.

     d) THE TWO BROKERS QUOTE THE SAME EXCHANGE CHARGE IN DIFFERENT WORDS, and
        it cost real time to prove it. Zerodha publishes NSE cash-market
        transaction charges as 0.00307%; Groww publishes 0.00297% and lists the
        investor protection fund charge separately. An exchange-set charge
        cannot differ by broker, so one of them had to be a restatement rather
        than a rate. NSE circular FA73061 settles it: per side, the EXISTING
        split is Rs 297 transaction + Rs 10 IPFT, the REVISED split is
        Rs 306.99 + Rs 0.01, and both total Rs 307 per crore. Groww quotes the
        old split, Zerodha the new. costs/model.py therefore carries ONE shared
        split at NSE's current values and lets ONLY brokerage differ between
        the two tables, and test_costs.py pins the Rs 307 per side so a future
        edit cannot quietly reintroduce a per-broker exchange rate. Inventing
        a per-broker split would have been invention; the verified fact is the
        total.

     Nine mutation probes were run against the finished layer and all nine were
     caught: exclusive-vs-inclusive boundary, a missing ATR waving a name
     through, the time gate running when unconfigured, unreadable screens
     counted as unreachable, the screen running after the rules, the screen
     recording without filtering, the screen running before suppression,
     headroom leaking into the ranking, and the check never being attached to
     the candidate.

     KNOWN GAPS, all deliberate and all open:
       - NEITHER schedule's rates have been reconciled against a real contract
         note. Both are published tables transcribed by hand. Do that before
         any figure computed from either is quoted as fact.
       - THE SPREAD IS NOT IN THE MODEL AT ALL, and at a one-minute horizon it
         is frequently the largest cost of the round trip. The hurdle is
         therefore a FLOOR, not an estimate. When MarketContext grows
         microstructure fields the spread belongs in
         FeasibilityPolicy.evaluate, in the same place and for the same reason.
       - max_atr_multiple is a placeholder like any threshold in rules.py. It
         has NO DEFAULT on purpose: a caller must state the assumption.

  6. DONE 2026-09-23: the buying model and decision-time sizing
     (costs/sizing.py, cli/check_costs.py). The user fixed the clip: "fixed
     value of buying at 1lakh inr, and sells would be all positions held", and
     asked that the cost model be "documented and coded for estimates during
     trade decisions". model.py works in fraction space and is what the scanner
     screens with; sizing.py is the layer that turns a quote into whole shares
     and a required fraction into a price the exchange will accept.

     FOUR THINGS THAT WILL BITE WHOEVER TOUCHES THIS NEXT:

     a) QUANTITY IS INTEGRAL, SO THE CLIP IS NEVER THE NOTIONAL. The clip is a
        FLOOR: a one-lakh clip at Rs 2,450 is 41 shares = Rs 1,00,450, because
        40 shares is Rs 98,000 and that is not a lakh. Every fraction in the
        model is a fraction OF NOTIONAL, so passing target_notional where the
        filled value belongs prices a trade that was never placed. The error is
        under 2% -- too small to look wrong, far too large against a target
        measured in tenths of a percent. A mutation probe for exactly this was
        run and caught by three tests.

     b) EXITS ROUND AWAY FROM THE ENTRY, AND THIS IS CORRECTNESS NOT TASTE.
        Long exits round UP to a tick, shorts round DOWN. Rounding to the
        NEARER tick is the realistic mistake: it leaves a long's exit a shade
        under the price that pays for the round trip, so the trade fills, looks
        like a win, and returns less than the margin that justified it. That
        exact mutation (both roundings to ROUND_HALF_EVEN) was applied and
        caught. Five probes total against sizing.py, five caught.

        The test that defends it does not hunt for a price where nearest
        rounding misbehaves; it asserts the stronger property that the chosen
        exit is the TIGHTEST tick that clears -- it pays, and one tick closer
        to the entry does not.

     c) THE TICK IS A FLOOR ON HOW FINE A TARGET CAN BE. tick_fraction is
        tick/price and moves inversely with price. At Rs 2,450 a 5-paisa tick
        is 0.002% and rounding is noise. At Rs 100 it is 0.05% -- HALF of a
        0.1% target -- so the exit can only land on the 5-paisa grid and what
        the trade asks for depends on where the entry sits in that grid, not
        on the target. Measured at the 0.1% target: an entry at Rs 100.00 is
        exactly on a tick and the exit returns the Rs 17.32 asked for, while
        an entry one tick higher at Rs 100.05 must jump to Rs 100.20 and
        returns Rs 67.30 -- nearly FOUR TIMES the target off a five-paisa
        difference in entry. That overshoot is not a bonus: the trade is now
        asking the market for a move four times larger, so it fills far less
        often. CHEAP STOCKS ARE A COARSER INSTRUMENT FOR THIS STRATEGY THAN
        EXPENSIVE ONES. If a liquidity filter ever admits sub-Rs-200 names,
        this is the number that says what it costs.

     d) "0.2% IN TOTAL" WAS AMBIGUOUS BY A THIRD OF THE TARGET; IT IS NOW
        STATED. Read as the amount KEPT AFTER charges it needs a 0.2827%
        gross move; read as the GROSS MOVE it keeps 0.1173%. At 0.1% it is
        worse: 0.1827% needed versus 0.0173% kept, which is Rs 17.32 on a
        lakh -- the charges take four fifths of it. THE SECOND READING IS THE
        ONE THE STRATEGY MEANS: STATED_GROSS_TARGET is 0.2% ABOVE THE BUY
        PRICE, so net profit is 0.2% minus the cost fraction.
        SizingPolicy.from_gross_target does the conversion in one place and
        RAISES on a target its own costs consume -- at GROWW's rates 0.2% at
        a Rs 20,000 clip is a loss, and it takes about Rs 28,690 to break
        even. At ZERODHA's it never raises, because that schedule never costs
        more than 0.1063% at any size above Rs 200 and so clears 0.2% at every
        clip. Which is why the schedule is an ARGUMENT to the conversion and
        not an import inside it. Converting once at the clip is safe in the
        only direction that matters -- the clip is the SMALLEST permitted fill
        and so the most expensive as a fraction, so every real name faces a
        hurdle at or BELOW the stated figure. check_costs still prints both
        readings, and a test pins that it keeps doing so.

     Shape decisions worth knowing the reason for:
       - Both exits are priced and neither is chosen. Importing Direction from
         scanner/models.py would invert scanner -> costs and break the
         stdlib-only contract that an AST-walking test enforces. Cost is
         direction-symmetric anyway.
       - A single quantity serves both legs, so A PARTIAL EXIT CANNOT BE
         EXPRESSED. That is the stated model, and a test pins the shape so the
         day scaling out is wanted it arrives as a visible change.
       - It lives in costs/ and not a new position/ package, because roadmap
         item 10 owns that name.
       - A stock quoted above the whole clip is an ORDINARY case, not an
         error: it buys one share, overshoots, and excess_notional reports by
         how much. NSE lists such names. Nothing raises and nothing returns a
         zero notional -- under a floor there is no quantity-zero case for a
         division by notional to fall into.
       - FIXED_CLIP_NOTIONAL is a named constant a caller passes in, not a
         default inside SizingPolicy. It is a stated strategy parameter.
       - tick_size DEFAULTS but max_atr_multiple does not, and the line between
         them is section 7.2: a published market fact may be defaulted, a
         strategy opinion may not.

     check_costs is the first check that needs NO BROKER AND NO SESSION, so it
     has no configuration branch and no exit code 2. Its docstring and its
     test's docstring both say so; ARCHITECTURE.md 4.11 no longer claims
     uniform exit codes across all of them.

     KNOWN GAP, open: NSE_EQUITY_TICK is the common cash-segment value, but the
     authoritative tick is PER INSTRUMENT and Instrument carries only exchange
     and trading_symbol -- nothing in src/ can look up the real one. On a name

     conservative in a way that shows up as an OVERSHOOT, which reads like the

13. SOURCE INDEPENDENCE AND NO LOOKAHEAD
----------------------------------------

The property that makes replay worth building: at any historical time t, the
scanner presents what it would have presented if t were NOW. Two halves, both
pinned by tests/test_source_independence.py against the whole chain rather
than against any single function, because neither is a property of a function.

  - SOURCE INDEPENDENCE. One deterministic session is expressed twice, as
    ticks through CandleBuilder and as OHLCVCandles through
    MarketState.backfill, then compared candle for candle, snapshot for
    snapshot and candidate for candidate. Values are regenerated on each side
    rather than copied, so a builder that mis-assembled a minute cannot
    supply its own answer to both sides of the comparison.

  - NO LOOKAHEAD. The snapshot at step k is identical whether the engine was
    fed k candles or the whole session, asserted at EVERY step rather than
    sampled -- a lookahead that only appeared once the 20-period window
    filled would sit in the middle of the session, where sampling the ends
    would miss it. This holds because warm_up is a convenience over update
    rather than a second implementation, and because
    minutes_since_session_open is arithmetic against 09:15 on the candle's
    own timestamp rather than a count of candles seen.

A third test is structural and covers what no fixture can. A wall-clock read
inside the decision path is reproducible in a test -- the test also runs now
-- and wrong in replay, where "now" is years after the candle. So it walks the
source of features/, scanner/ and costs/ with ast and fails on any clock read.
market/ is exempt on purpose: the volume poller stamps readings from the clock
to measure staleness and the stream transport uses a monotonic deadline, but
neither reaches a candle's values and no historical candle passes through
either. If a later layer needs the clock, put it where market/ is, not where
features/ is.

THE ONE ASYMMETRY THAT IS REAL is volume, and it is an asymmetry of knowledge
rather than of behaviour. A failed poll leaves a live minute's volume unknown,
a state the historical endpoint never reports because it always serves a
figure. Every affected feature is WITHHELD rather than estimated: readiness
flags fall in step with the values, no price or momentum feature moves, and a
candidate's evidence can only cite what its snapshot actually held. A live
scan therefore sees LESS than a replay of the same minutes, never something
different about the same question. For replay this means the VWAP rule is
exercised more often than a live session with an imperfect poller would,
so its measured contribution is an UPPER BOUND on its live one.

Two mutation probes confirm the tests bite rather than merely pass:
_to_candle stamping volume+1 kills two of them, and _volume_ratio returning
Decimal(0) instead of None -- the exact fabricated-zero the design refuses --
kills the withheld-volume test. Re-run both if either file is touched.

Residual hazard, documented rather than code-enforced: Candle carries no
completeness flag. CandleBuilder.flush() emits a candle covering part of a
minute that is indistinguishable from one covering all of it. Today the only
src/ caller is cli/check_market_state.py, which has no feature engine
attached, so nothing partial can reach the scanner. A future caller that
flushes into a feature engine would leak a partial candle undetectably. If one
is ever written, give Candle the flag rather than relying on the caller.
